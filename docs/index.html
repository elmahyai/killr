Kill R

R holds some of the best statistics code in the world, and it is trapped in R. killr translates the CRAN catalog into Python and Rust, and every translated function is checked against the original R output. This page shows the live progress.

About

How do you tackle a catalog this hard?

Twenty-five thousand packages, compiled kernels, and a proof for every function. The hard part is not one clever prompt. It is knowing which work is judgment, which work should become a program, and how a mistake is written down so it is not made twice.

1

How do you reduce repeated tasks?

When a step is deterministic, we do not keep paying a model to do it. We have the model write a program, then we run the program. Screening tarballs used to be an AI job: open a package, list the Fortran, count the R files, read Depends. That is mechanical. So the model wrote a prepare program. The program opens each tarball once under rcran/contrib and writes one SQLite database. Agents do not invent the inventory, and they do not write this page. Progress by package and How we handle low-level code are that inventory.

Progress by package

R files, exported functions, and the packages in Depends and Imports. A package is free when those dependencies are already finished or replaced. Suggests and Enhances do not block. Base R is not opened as a package.

Low-level code

Fortran, C, and C++ files and line counts, plus whether a Rust crate already covers the kernel. A package whose compiled code computes is later given a -low plan. A thin wrap around an existing C++ system is routed, not rewritten.

Priority

When several packages are free, the next one is the highest last-month download rank from the RStudio CRAN mirror. A dependency of a listed package is opened before that package. A package already on the replaced list is a stand-in, not a translation.

2

What is still a job for the model?

Judgment that is not a lookup: remaking an algorithm, choosing wrap versus remake, writing the Python or the crate. Each free package goes to translation agents. They read the constitution and the plan stored on that package. They write Python under packages/<Name>, and they write Rust under crates/<name> when the work is a compiled kernel. The source is the tarball on disk, not GitHub.

Constitution

One set of rules for every agent: what counts as translated, the order of work, routing to stand-ins, wrapping versus remaking, and the Rust kernel rule. S3, S4, R6, and S7 are not copied as object systems. The translation is a Python class or a Rust struct, and the method body is an ordinary function.

Wrapping or remaking

When R only wraps a C++ system, Python or Rust wraps that same system. The R glue is not translated. When the algorithm is original to R, including a kernel written in C++ or Fortran, the algorithm is remade. That kernel lives in its own crate and is loaded, not ported again.

Routing, not rewriting

Some R packages are a thin wrap around a system that already exists. Those are recorded as replaced and are not translated. A new big library is named and agreed before it is used.

How a batch runs

Easier first-pass Python uses a faster model. Work that already has a matching lesson, a new crate, or a failed proof uses a stronger thinking model. A batch returns three things: the proof, any packages it is waiting on, and at most one new lesson. If a function calls another package that is not yet translated, it is marked waiting and the next package opened is one of those names.

3

How do you improve over time?

A mistake is written down once. Each pitfall becomes one short lesson file, named after the fact — not after the package, and not after the day it was found. Later agents open at most three matching files before they start. A new fact goes in the file whose name already describes it, so the same lesson is not written twice under two titles.

One file per fact

The file name is the fact. Fortran pair loops, timezone names, a stub that must stay a stub. The next agent that hits that fact opens that file. It does not invent a second explanation.

At most three lessons

An agent does not read the whole experience folder. It picks at most three files whose names match the work in front of it. That keeps the start of a batch short, and it keeps the lessons from turning into a second constitution.

One new lesson per batch

A batch may add at most one new lesson. Review rounds feed new pitfalls back the same way. The system gets sharper without growing a pile of overlapping notes.

4

How do you know it is not a guess?

The model does not grade itself. A proof is another program: an R script and a Python script on the same input. The outputs must match. That is how we catch a silent mistake. The printed or drawn pair is saved, and the dashboard shows it next to the function. Nothing counts as done until that check passes.

Match

The outputs must agree within 1e-8. The proof compares values, not object-system dispatch. A function whose note begins with Left is reserved, not claimed.

Speed

One untimed call, then the median of 20. R uses Sys.time(). Python uses time.perf_counter(). Speedup is the R time divided by the Python time.

What is saved

The two scripts live under packages/<Name>/proof. What they print or draw is saved under packages/<Name>/docs/output/. A .txt file is shown as text. An .svg file is shown as the figure.

5

How do we get the best out of this?

The same answers, again. Repeated work becomes a program. A new pitfall becomes a lesson. A function is finished only when the proof matches. The first translations already exist. The work ahead is finish the first round, review again, raise Rust, and integrate into the frameworks that already exist.

Finish the first round

A first translation for every package that is not replaced. The database already splits compiled kernels from the R side. Free packages go to agents. A package waiting on Depends is opened after that dependency. A function is finished only when it matches R. Coverage first; the later rounds make it better.

  • Screen and prioritize the rest of the catalog
  • Translate every free package
  • Prove each function against R
  • Clear the packages still in progress

More review rounds

A first pass can pass its proofs and still miss an edge. Later rounds add more proofs, cover the cases the first example did not, and write the new pitfalls down so the next agents do not repeat them.

  • Review every complete package again
  • Add more proofs, not only the first example
  • Resolve the checks that do not match yet
  • Feed what we find back into experience

Raise Rust coverage

More compiled kernels become Rust crates, so they run without a C or Fortran toolchain. We also decide, function by function, what should live in Rust instead of Python: the heavy numerics, the tight loops, anything that is better as a crate.

  • Turn more Fortran and C kernels into crates
  • Move more Python numerics into Rust where that is the better home
  • Show Rust coverage next to the function counts

Integrate into existing frameworks

A third level after translation and review. If a translated piece already fits a mature Rust or Python library — a grid, a data frame, a chart — we integrate with that library and use it here, instead of keeping a parallel copy. The proof still compares against R.

  • Look for a mature home for each translated system
  • Wrap or extend that library when the fit is real
  • Keep the R proof after the integration
