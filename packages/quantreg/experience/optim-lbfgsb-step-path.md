nlrq picks each step length with R's optim, method L-BFGS-B, bounds 0 to 1, factr 1e7, and a numerical gradient with ndeps 1e-3. SciPy's L-BFGS-B returns a slightly different lambda when the search is not clean, and the outer path then drifts. For the tau = 0.5 check the lambda sequence agrees with R's to about 7 digits and the fit matches to about 5e-13. For tau = 0.25 the first three lambdas are 1, then R gives 0.2510625 and SciPy gives 0.2510630. The coefficients differ by 1e-7 to 2e-7 (R 2.6199838 vs SciPy 2.6199841), while the deviance agrees to about 1e-9. A bounded Brent search gives a different answer again, so matching other taus needs R's own L-BFGS-B kernel, vendored as a crate.

Update: the kernel is now crates/rlbfgsb. Fed R's exact objective values for each outer step, it returns R's lambda with zero difference at all six steps, including the same function counts. The remaining gap is rounding in the step coefficient, not the optimizer. Step 1 agrees with R to about 3e-16. That moves the parameters by an ulp, and numericDeriv's forward difference (step about 1.5e-8) amplifies it into about 1e-9 in the gradient, so the path drifts. Porting lsfit to LINPACK's Householder order did not close the gap (it made tau 0.25 worse). The current result is 1.2e-8 from R at tau 0.25, 1.4e-12 at tau 0.5, and 2e-14 at tau 0.75. Getting below 1e-8 at tau 0.25 needs R's BLAS summation order bit for bit.
